1. rdt3.0 recap: lossy channels

Reliable Data Transfer slides (rdt3.0) · Kurose & Ross 3.4.1

rdt3.0 is where the post-midterm material starts: rdt2.2 plus a timer, so the sender can recover from loss. Still one packet at a time.

  • The new problem:
    • The channel can now lose packets as well as corrupt them.
    • Kept from rdt2.2: checksums, sequence numbers (0/1), ACKs that carry a number, retransmission.
    • Added: a countdown timer and retransmission on timeout.
  • Timer rules:
    • Start the timer every time a packet is sent, new or retransmitted.
    • Stop it when the correct, uncorrupted ACK arrives.
    • Timeout: resend the packet and start the timer again.
    • The timeout is chosen so loss is likely, not guaranteed.
  • Why "always retransmit" works:
    • No ACK could mean the data was lost, the ACK was lost, or either was just slow.
    • The sender can't tell these apart, and doesn't need to: it retransmits in every case.
    • A delayed packet that looks lost causes a duplicate. Sequence numbers let the receiver spot it.
  • Sender FSM (four states):
    • Wait for call 0 from above → rdt_send(data): send pkt0, start timer.
    • Wait for ACK0 → intact ACK0: stop timer, go to Wait for call 1.
    • In Wait for ACK0: a corrupted ACK or an ACK1 → Λ (no action); the timer handles recovery.
    • In Wait for ACK0: timeout → resend pkt0, start timer.
    • Wait for call 1 from above and Wait for ACK1 mirror these with 1 and 0 swapped.
    • In either "wait for call" state, any arriving packet → Λ. Nothing is outstanding, so a stray or duplicate ACK changes nothing (in-class Q1).
  • Receiver:
    • Same FSM as rdt2.2: deliver new data and ACK it with its number; re-ACK duplicates without delivering them.
    • With sequence numbers alternating 0, 1, 0, 1, rdt3.0 is the alternating-bit protocol.
  • The four operation cases:
    • No loss: 0, 1, 0, … each ACKed once.
    • Packet lost: the timer expires, the same packet is resent.
    • ACK lost: the timer expires, the receiver sees a duplicate, discards it and re-ACKs.
    • Premature timeout (delayed ACK): a duplicate is sent and discarded; the sender ignores the extra ACK. Correct, just wasteful.

2. Stop-and-wait performance and pipelining

Reliable Data Transfer slides · Kurose & Ross 3.4.2

rdt3.0 works but wastes the link. Pipelining keeps several packets in flight to fill the idle time.

  • Terms:
    • L: packet length in bits. R: link rate in bits per second.
    • L/R: transmission time, how long it takes to push one packet onto the link.
    • RTT: round-trip time.
    • Utilization U: the fraction of time the sender is actually transmitting.
  • Stop-and-wait:
    • Send one packet, then wait for its ACK. The ACK arrives at t = RTT + L/R.
    • U_sender = (L/R) / (RTT + L/R)
    • Example: L = 8,000 bits, R = 1 Gbps → L/R = 0.008 ms; RTT = 30 ms.
    • U = 0.008 / 30.008 ≈ 0.00027. Throughput ≈ 8,000 bits / 30.008 ms ≈ 267 kbps on a 1 Gbps link.
    • The protocol itself is the bottleneck. Processing and queuing delays make it worse.
  • Pipelining:
    • The sender sends several packets before waiting for ACKs; packets in transit form a pipeline.
    • U_sender = N·(L/R) / (RTT + L/R), capped at 1
    • 3 packets → 3 × 0.008 / 30.008 ≈ 0.0008, three times stop-and-wait.
    • To keep the sender always busy: N ≥ (RTT + L/R) / (L/R).
  • What pipelining does not change (in-class Q3):
    • Each packet still takes L/R to transmit.
    • Each packet still has the same propagation delay.
    • Once the sender transmits continuously, a bigger window adds nothing.
  • Consequences of pipelining:
    • A larger sequence-number range: every unACKed packet needs a unique number.
    • Sender buffering of unACKed packets, for possible retransmission.
    • Sometimes receiver buffering of out-of-order packets that arrived intact.
    • An error-recovery strategy: Go-Back-N or Selective Repeat.
  • Why 1 bit isn't enough (in-class Q4):
    • Send three messages labelled 0, 1, 0: two outstanding messages share label 0.
    • An ACK0 can't say which one it confirms. No corruption is needed for the ambiguity.
    • k-bit sequence numbers give the range 0 to 2ᵏ − 1, with modulo-2ᵏ arithmetic (a ring).

3. Go-Back-N

Reliable Data Transfer slides · Kurose & Ross 3.4.3

A sliding window of up to N unACKed packets, cumulative ACKs, one timer, and a receiver that throws away anything out of order.

  • Sender window:
    • At most N unACKed packets in the pipeline (the window size). A sliding-window protocol.
    • send_base: the oldest unACKed sequence number. nextseqnum: the next number to use.
    • [0, send_base − 1]: already ACKed.
    • [send_base, nextseqnum − 1]: sent, not yet ACKed (in flight).
    • [nextseqnum, send_base + N − 1]: usable, not yet sent.
    • Beyond send_base + N − 1: not usable yet.
  • Sender actions:
    • Data from above: send it if the window has room; otherwise refuse or buffer it.
    • Cumulative ACK(n): every packet ≤ n arrived. send_base becomes n + 1.
    • One timer, for the oldest unACKed packet. Restart it when the base moves and packets remain; stop it when nothing is outstanding.
    • timeout(n): resend packet n and every later packet in the window.
    • Duplicate ACKs (for data already confirmed) are ignored.
  • Receiver:
    • Always ACKs the highest in-order sequence number received, so duplicate ACKs are normal.
    • Tracks only rcv_base, the next number it expects.
    • Out-of-order packet: discard it (as presented; buffering is a design choice) and re-ACK the last in-order packet.
    • Why discard: the sender will resend it anyway, and the receiver stays simple.
  • Cumulative ACKs cover lost ACKs (in-class Q5):
    • Sent 0–3; ACK0, ACK1, ACK2 lost; ACK3 arrives before the timeout.
    • ACK3 proves 0–3 all arrived: send_base = 4, stop the timer, resend nothing.
  • Limits:
    • One error forces resending many packets that already arrived. Big windows and high error rates clog the pipe.
    • Window limit with k-bit numbers (textbook): N ≤ 2ᵏ − 1.

4. Selective Repeat

Reliable Data Transfer slides · Kurose & Ross 3.4.4

Resend only what was lost: individual ACKs, a timer per packet, and a receiver that buffers. The price is a stricter limit on the window.

  • The idea:
    • Retransmit only the lost or corrupted packets.
    • Each correctly received packet is individually acknowledged.
    • Window size N, but some packets inside the sender's window may already be ACKed.
    • The receiver buffers out-of-order packets and delivers them in order once the gap fills.
  • Sender actions:
    • Data from above: send it if its sequence number is in the window; otherwise buffer or refuse it.
    • Timeout: each packet has its own logical timer; only that packet is resent. One hardware timer can simulate many logical ones.
    • ACK received: mark that packet ACKed. If it was send_base, slide the window to the next unACKed packet and send any newly allowed packets.
  • Receiver actions:
    • Packet in [rcv_base, rcv_base + N − 1]: send a selective ACK; buffer it if new; if it equals rcv_base, deliver it plus the consecutive buffered packets and slide the window.
    • Packet in [rcv_base − N, rcv_base − 1] (already received): re-ACK it. Otherwise a lost ACK would leave the sender's window stuck.
    • Anything else: ignore it.
    • The sender's and receiver's windows don't always line up.
  • The SR dilemma:
    • Sequence numbers 0–3, window 3. Packets 0, 1, 2 arrive and are delivered; the receiver's window becomes 3, 0, 1.
    • Case (a): the ACKs arrive, and the sender sends new packets 3, 0. The new pkt0 is accepted. Fine.
    • Case (b): every ACK is lost, so the sender resends old pkt0. The receiver accepts it as new. Wrong!
    • The receiver can't see the sender's side; both cases look identical to it.
    • Rule: window ≤ half the sequence-number space (N ≤ 2ᵏ⁻¹). 3 bits → 8 numbers → N ≤ 4.

5. TCP connections and the segment

TCP slides · Kurose & Ross 3.5.1–3.5.2

TCP is a connection between two hosts and nothing in between. Its header carries what reliability, flow control and connection management need.

  • What a TCP connection is:
    • Connection-oriented: a handshake comes before data, and both sides set up state variables.
    • Logical, not physical: the relationship exists only at the two end hosts.
    • Routers forward IP datagrams without TCP state (some middleboxes, such as firewalls and NATs, may inspect or track it).
    • Full-duplex: data flows both ways at once.
    • Point-to-point: one sender, one receiver. No multicast.
    • A connection = buffers, state variables and socket endpoints at both hosts.
  • Setting up:
    • The host that initiates is the client, e.g. clientSocket.connect((serverName, serverPort)).
    • Three-way handshake: (1) the client sends a special segment; (2) the server replies with another; (3) the client replies again, possibly with data.
    • Textbook names: SYN, SYNACK, ACK. FIN closes, RST resets.
  • Moving data:
    • The app writes into the socket → TCP's send buffer.
    • TCP cuts segments of up to MSS (Maximum Segment Size): the most application data per segment, header not included.
    • MSS is based on the link-layer MTU (Ethernet: 1,500 bytes) → typically 1,500 − 20 (IP) − 20 (TCP) = 1,460.
    • Segments go into IP datagrams. At the far end, data lands in the receive buffer and the app reads from it.
    • Each side has its own send and receive buffers.
  • Recovery lives at the ends:
    • Discussion question: a router drops a datagram carrying TCP data, and has no copy of the connection's state.
    • The sender still holds the unACKed data and retransmits after a timeout or duplicate ACKs.
    • The receiver's sequence/ACK state shows what is missing. The router never needs to rebuild the stream.
  • Segment structure (32 bits wide):
    • Source port, dest port: 16 bits each.
    • Sequence number (32 bits): counts bytes of data, not segments.
    • Acknowledgment number (32 bits): the next byte expected.
    • Header length (4 bits): in 32-bit words; 5 words = 20 bytes with no options.
    • Flags: C, E congestion notification · A the ACK field is valid · RST, SYN, FIN connection management · U, P urgent and push.
    • Receive window (16 bits): flow control, the bytes the receiver will accept.
    • Checksum (16 bits), urgent data pointer, then variable-length options.
    • Then the application data (variable length).

6. Sequence numbers and ACK numbers

TCP slides · Kurose & Ross 3.5.2

TCP numbers bytes. A segment's sequence number is its first byte; an ACK names the next byte the receiver wants.

  • Sequence numbers:
    • TCP treats data as an unstructured but ordered stream of bytes.
    • A segment's sequence number = the byte-stream number of its first byte.
    • MSS = 1,000: segment 1 is bytes 0–999 (Seq 0), segment 2 is 1,000–1,999 (Seq 1,000), and so on.
    • The initial sequence number is random, so old segments aren't confused with a new connection.
  • ACK numbers:
    • ACK = the next byte expected from the other side.
    • Cumulative: acknowledges every byte up to the first missing one.
    • Bytes 0–535 received → ACK = 536. Bytes 1,000–1,099 received → ACK = 1,100.
    • Compare GBN: ACK(n) there means "I have n"; in TCP it means "send me n next".
  • Out-of-order segments:
    • The TCP spec doesn't say what to do; it's up to the implementer.
    • Options: discard them, or buffer them until the gap fills (more efficient, used in practice).
  • Full-duplex and piggybacking:
    • Each direction is its own byte stream with its own sequence numbers.
    • A segment can carry data and ACK the other side's data at the same time.
    • Telnet example: A → B Seq=42, ACK=79, 'C'. B → A Seq=79, ACK=43, 'C' (ACKs and echoes it). A → B Seq=43, ACK=80.
    • Each ACK is one more than the sequence number received, because each segment carried one byte.

7. RTT estimation and timeout

TCP slides · Kurose & Ross 3.5.3 (the EWMA formulas are from the textbook)

TCP needs a timeout a bit longer than the RTT, but the RTT keeps changing. So it averages samples and adds a margin that grows with variation.

  • Choosing the timeout:
    • It must be longer than the RTT, but the RTT varies.
    • Too short → premature timeouts and unnecessary retransmissions.
    • Too long → slow reaction to real segment loss.
  • Measuring:
    • SampleRTT: time from sending a segment to receiving its ACK.
    • TCP measures one SampleRTT at a time, not one per segment.
    • No samples from retransmitted segments: the ACK could belong to either copy.
    • Samples fluctuate with congestion and host load, so one sample isn't representative.
  • Smoothing (textbook):
    • EstimatedRTT = (1 − α)·EstimatedRTT + α·SampleRTT, α = 0.125
    • An exponentially weighted moving average (EWMA): a past sample's weight shrinks by (1 − α) with each newer sample, but never reaches zero.
    • DevRTT = (1 − β)·DevRTT + β·|SampleRTT − EstimatedRTT|, β = 0.25
    • DevRTT estimates how much SampleRTT varies from the average.
    • TimeoutInterval = EstimatedRTT + 4·DevRTT
    • In textbook problems, update EstimatedRTT first, then use the new value in DevRTT.
    • An initial TimeoutInterval of 1 second is recommended.
    • After a timeout, TCP doubles the interval instead of using the formula, until new data is ACKed.

8. TCP reliable data transfer

TCP slides · Kurose & Ross 3.5.4

TCP mixes the two pipelined schemes: cumulative ACKs like GBN, but it resends one segment at a time, like SR. Duplicate ACKs let it resend before the timer fires.

  • Sender events:
    • Data from the application: put it in a segment with the next sequence number, pass it to IP, start the timer if none is running (it times the oldest unACKed segment).
    • Timeout: retransmit the segment that caused the timeout, then restart the timer.
    • ACK received: compare with SendBase (the oldest unACKed byte). If ACK > SendBase, new data is confirmed: update SendBase and restart the timer if unACKed data remains.
  • Receiver ACK generation:
    • In-order segment, everything before it already ACKed → delayed ACK: wait up to 500 ms for another segment; if none comes, send the ACK.
    • In-order segment, another segment's ACK pending → immediately send one cumulative ACK for both.
    • Out-of-order segment (a gap) → immediately send a duplicate ACK for the next expected byte.
    • Segment that partly or fully fills a gap → immediately ACK, if it starts at the low end of the gap.
  • Scenario 1, lost ACK:
    • A sends Seq=92 (8 bytes); B's ACK=100 is lost.
    • Timeout → A resends Seq=92. B already has those bytes: discard, ACK=100 again.
  • Scenario 2, premature timeout:
    • A sends Seq=92 (8 bytes) and Seq=100 (20 bytes). B sends ACK=100 and ACK=120, but both are delayed past the timeout.
    • Timeout → A resends only Seq=92 and restarts the timer.
    • If ACK=120 arrives before the new timeout, Seq=100 is never resent. B answers the duplicate with a cumulative ACK=120.
  • Scenario 3, cumulative ACK covers a lost ACK:
    • ACK=100 is lost, but ACK=120 arrives before the timeout.
    • ACK=120 confirms both segments, so nothing is resent.
  • Fast retransmit:
    • The sender waits for 3 duplicate ACKs (4 ACKs for the same data in total).
    • It takes this as loss of the segment after the last in-order byte.
    • It retransmits immediately, before the timeout, cutting the delay.
    • Why three: reordering alone can cause one or two duplicates.
  • GBN or SR?
    • Cumulative ACKs: GBN-like.
    • Resending one segment on timeout, and receivers that buffer out-of-order data: SR-like.

9. TCP flow control

TCP slides · Kurose & Ross 3.5.5

The receiver tells the sender how much free buffer it has, and the sender never has more than that in flight.

  • The problem:
    • The network layer can deliver data faster than the application reads it from the socket.
    • Each host has a receive buffer. A slow reader plus a fast sender → overflow.
  • Flow control:
    • Keeps the sender from overwhelming the receiver's buffer: a speed-matching service.
    • Distinct from congestion control, which is about the network, not the receiver.
  • The receive window:
    • rwnd = the free buffer space at the receiver.
    • The receiver (Host B) advertises rwnd in the receive window field of every segment it sends.
    • LastByteRead: last byte the app read. LastByteRcvd: last byte placed in the buffer.
    • rwnd = RcvBuffer − (LastByteRcvd − LastByteRead)
    • The sender (Host A) tracks LastByteSent and LastByteAcked.
    • LastByteSent − LastByteAcked ≤ rwnd
    • That guarantees the receive buffer can't overflow.
    • RcvBuffer is set by socket options, typically 4,096 bytes by default; many OSes auto-adjust it.
  • Zero window:
    • If rwnd = 0 and the receiver has nothing to send, the sender could be blocked forever.
    • Fix: the sender keeps sending 1-byte probe segments; their ACKs eventually advertise a non-zero window.
  • UDP for comparison:
    • No flow control. Segments go into a finite buffer.
    • If the app reads too slowly, the buffer overflows and segments are lost.
